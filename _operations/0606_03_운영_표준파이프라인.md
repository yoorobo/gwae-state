# 표준 파이프라인 (CASHMONTH PIPELINE v1) + GWAE 순서 평가

> 목적: 솔로파운더가 5에이전트로 매출을 내는 **검증된 표준 작업 순서**를 박제하고,
> GWAE가 실제로 밟은 순서를 그 위에 겹쳐 빠진 단계·역전된 순서를 평가한다.
> 다음 베팅(1번 실험체)은 이 파이프라인을 처음부터 타고 간다.
> 이 문서는 집2(운영체계)다. 제품과 무관하게 영속한다.

---

## PART 1 — 기준선: 무엇을 종합했나

세 출처를 합쳐 파이프라인을 역산했다.

1. **빅테크 0→1 절차** (Steve Blank / Lean Startup): 고객발견 → 고객검증 → 제품개발 → 알파/베타 → 출시. 핵심 = "코드 한 줄 전에 수요 검증."
2. **2026 솔로파운더 성공 공통분모** (Pieter Levels $3M, Midjourney $18M/인, Base44 6개월 $80M 매각, Danny Postma $3.6M): 좁고 고의도(high-intent) 문제 → 빠른 수요검증 → 린 스택으로 MVP → 측정 → 반복. 공통적으로 **검증→빌드 순서**를 지킴.
3. **하네스/컨텍스트 엔지니어링** (2026 정설): 솔로파운더의 진짜 스킬은 AI 사용이 아니라 **오케스트레이션**. CLAUDE.md·MCP·구조화 메모리로 에이전트 환경을 설계해 "반복 가능"하게 만드는 것. 한 번 겪은 사고를 시스템에 박아 다음에 안 겪게 함.

## PART 2 — CASHMONTH 표준 파이프라인 v1

각 단계 = **게이트(통과조건) + 담당 에이전트 + 산출물**. 게이트를 통과 못 하면 다음 단계로 못 감.

### P0. 문제·타겟 발견 (Discovery)
- **게이트 G0**: "누가, 어떤 고의도 고통을, 돈 내고서라도 풀려 하는가"가 한 문장으로 적혔는가.
- 담당: 제나(시장·커뮤니티 리서치) → 차이(타겟 가설 정리)
- 산출물: 타겟 1문장 + 고통 근거(커뮤니티 실제 발화)
- 원칙: **제품 아이디어보다 타겟이 먼저.** 솔루션이 문제를 찾아다니면 안 됨.

### P1. 수요 검증 (Validation) — 코드 전(前)
- **게이트 G1**: 페이크도어/랜딩으로 **측정된 수요 신호**(클릭률·등록률)가 목표치를 넘었는가.
- 담당: 클로(랜딩 설계) → 레오(랜딩 구현) → 도우(배포·측정 검증)
- 산출물: 라이브 랜딩 + GA4/측정 동선 검증 PASS + 신호 데이터
- 원칙: **검증 전 제품 코드 금지.** 여기서 막히면 파이프라인 자체가 없는 것.

### P2. MVP 설계·결정 (Spec & Decide)
- **게이트 G2**: 모든 제품 결정이 **ADR 단일소스 한 곳**에 적혔는가. 기획서/코드/대화 여러 곳에 흩어지지 않았는가.
- 담당: 차이(스펙) → 클로(ADR 압축) → 정학(승인)
- 산출물: ADR(결정기록), EARS 요건정의
- 원칙: **결정은 한 곳에서만.** 두 곳에 적히면 반드시 어긋난다.

### P3. 구현 (Build)
- **게이트 G3**: 추론/뮤테이션 분리가 지켜졌는가(추론=문서만, 뮤테이션=코드만). 검증 통과 후 머지인가.
- 담당: 레오(구현) / 도우(검증·쉘) / 정학(머지 승인)
- 산출물: 동작 코드 + 검증 결과(result.md push)
- 원칙: 선빌드 금지. 검증 후 배포.

### P4. 측정·학습 순환 (Measure-Learn)
- **게이트 G4**: 트래픽 채널마다 **측정 링크가 박혀** 있는가. 학습 데이터가 0이 아닌가.
- 담당: 클로(채널 설계) → 도우(측정 검증)
- 산출물: 채널별 측정링크 + 유입·전환 데이터
- 원칙: **채널엔 측정링크 필수.** 측정 없는 활동은 학습이 아니라 소모.

### P5. 반복 or 피벗 (Iterate/Pivot)
- **게이트 G5**: 데이터가 가설을 지지하는가. 아니면 타겟·채널 피벗.
- 담당: 차이(데이터 해석·반론) → 정학(피벗 결정)
- 원칙: 의견 아닌 데이터로 방향 결정.

### 전(全)단계 횡단 — 하네스 (Harness)
- 각 단계 사고에서 게이트를 1개씩 뽑아 이 파이프라인에 박는다(포스트모템→프로세스).
- 컨텍스트: STATE/HANDOFF/ADR/CLAUDE.md 단일진실원으로 에이전트 환경 고정.
- 이게 "200명 대체"의 실체 = 사고를 시스템에 박아 다음 제품이 안 겪게 함.

## PART 3 — GWAE 순서 평가 (표준 위에 겹치기)

GWAE가 실제로 밟은 순서를 P0~P5 위에 올린 결과.

| 표준 단계 | GWAE 실제 | 판정 | 어긋남 → 뽑은 게이트 |
|---|---|---|---|
| P0 발견 | 제품(큐브엔진) 먼저, 타겟은 "이직"→"연애"로 뒤늦게 변경 | ❌ 역전 | 솔루션이 문제를 찾아다님 → **G0: 타겟 먼저** |
| P1 검증 | 페이크도어 검증 전에 64괘 코어·ADR 다수 확정 | ❌ 역전 | 선빌드 → **G1: 검증 전 코드 금지** |
| P2 결정 | 작괘 상하괘가 기획서/코어 두 곳서 갈림, 나중에 차이가 발견 | ⚠️ 분산 | 결정 두 곳 → **G2: ADR 단일소스** |
| P3 구현 | 추론/뮤테이션 분리는 잘 지킴 (강점) | ✅ | — |
| P4 측정 | GA4 만들고 배포본 누락→광고 당일 발견 / 레딧 4일 측정링크 0 | ❌ 누락 | 게이트 부재 → **G3 검증후배포 + G4 측정링크필수** |
| P5 반복 | 측정 데이터가 빈약해 학습 순환이 약함 | ⚠️ 미약 | P4가 깨져서 P5도 약함(연쇄) |

### 핵심 진단
GWAE의 어긋남은 산발적 실수가 아니라 **하나의 구조적 패턴**이다:
> **"만들면서 검증·측정을 나중에 붙였다."** (Build-first)
> 표준은 그 반대 — **검증·측정을 먼저 깔고 만든다.** (Validate-first)

첫 프로젝트라 당연하다. P3(구현 규율)은 이미 강점이니, 다음 베팅은 **P0·P1·P4를 앞으로 당기는 것**만 고치면 된다.

## PART 4 — 다음 베팅(1번 실험체) 적용 규칙

다음 제품은 이 순서를 **건너뛰지 않고** 탄다:
1. P0 타겟 1문장 먼저 (G0 통과 전 제품 얘기 금지)
2. P1 랜딩+측정 먼저 띄우고 신호 확인 (G1 통과 전 코어 코드 금지)
3. P2 결정은 ADR 한 곳에만 (G2)
4. P3 검증 후 배포 (G3) — GWAE에서 유일하게 잘된 P3 규율 유지
5. P4 모든 채널에 측정링크 (G4)
6. P5 데이터로 반복/피벗 (G5)

이 6게이트가 CASHMONTH 운영체계의 첫 파이프라인 자산이다.
